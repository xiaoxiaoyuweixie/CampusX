# 聊天举报功能部署与验收

实现依据：[举报 PRD](../prd/report-feature-2026-09-12.md)。本文件用于发布准备；本地代码和测试通过不代表云函数、数据库、存储规则或客户端已经上线。

当前推进决定（2026-09-12）：用户已明确选择先采用云存储“所有用户可读，仅创建者可读写”模板，并继续云函数配置。下文按目录隔离的 JSON 仍是待验证方案，不代表用户当前选择或已经成功应用的云端规则。已告知的公开读取影响不在每一步重复要求确认。

## 发布顺序

1. 在测试云环境创建下述四个集合和索引，核对既有集合仍仅服务端读写。举报相关集合对所有客户端禁读、禁写。
2. 合并云存储规则，使正式举报证据对所有客户端禁读、禁写、禁删，临时举报文件仅上传者可访问。等待规则生效并实测绕过接口的访问被拒绝。
3. 新建 `reportService` 时选择 **Nodejs20.19**，上传完整目录及 `package-lock.json`，使用云端安装依赖；部署完整的 `adminService`，保持既有 HTTP POST `{ action, data }` 地址及鉴权。举报截图最多 9 张、每张 10 MiB，建议测试时配置 60 秒超时和至少 512 MB 内存，并依据真实下载、解码、转存耗时及内存峰值调优。
4. 在测试环境验证小程序提交与后台结案后，再发布小程序和管理端。小程序新增 `pages/report/index`，原聊天路径不变；管理端仍由 Vite 构建，无新增框架或环境变量。
5. 举报入口与服务可用时，同批部署 `aiAssistant` 的 `knowledge/rules.json` 和 `rules.md` 更新；不要提前让线上助手承诺尚不可用的入口。

不需要迁移旧聊天、商品或用户记录，不需要修改 `admin-web/.env`。生产发布及生产数据操作应在正式发布授权后执行。

### 图片解码依赖

`reportService` 固定使用 `sharp@0.35.3`，真正解码 JPEG/PNG/WebP，避免仅凭扩展名、文件头或 CRC 接受无法显示的证据。验证时生成的 1×1 内存输出直接丢弃，正式保存的仍是原始文件字节，不转码或修改用户证据。逐张校验、禁用解码缓存并限制线程并发，避免九张截图同时展开。

该版本需要 Node.js 20.9 及以上；CloudBase 提供 Nodejs20.19。仅新函数使用这一运行时，不修改既有云函数运行时。[Sharp 安装要求](https://sharp.pixelplumbing.com/install/)、[CloudBase 运行环境](https://docs.cloudbase.net/cloud-function/runtime-support)

部署时必须保留 optional dependencies，让云端安装适配 Linux/CPU 的 Sharp 与 libvips 二进制；不要上传 macOS 的 `node_modules`。如手动在目标 Linux 环境安装，使用 `npm ci --include=optional`。先在测试云函数验证 `require('sharp')` 以及真实 JPEG/PNG/WebP 提交能成功；不能只凭本机能加载二进制就认定云端安装完成。

## 数据库

| 集合 | 用途 | 客户端权限 |
| --- | --- | --- |
| `reports` | 完整原始材料、必要快照、正式证据引用、结案留痕；也是永久最小回执的数据来源 | 读/写均禁止 |
| `report_submissions` | 账号与稳定提交标识的材料指纹锁、事务终止标记，防止并发改写及明确拒绝后的迟到成功 | 读/写均禁止 |
| `report_pending_guards` | 按举报人和会话生成固定文档 ID，事务内保证最多一份待处理举报 | 读/写均禁止 |
| `report_evidence_uploads` | 将临时上传路径绑定真实举报人、会话、提交标识、附件标识与格式 | 读/写均禁止 |

每个新集合采用管理员/服务端独占权限，等价自定义规则为：

```json
{ "read": false, "write": false }
```

`reports` 创建两个非唯一复合索引：

- `status` 升序、`createdAt` 降序、`_id` 降序：状态筛选及分页。
- `createdAt` 降序、`_id` 降序：“全部”列表。

部署时以实际查询的控制台提示确认索引。提交与结案的互斥依赖固定文档 ID 的数据库事务，不用“先查询再新增”或仅前端按钮禁用来替代。`reports` 的新状态为 `pending`、`substantiated`、`unsubstantiated`；结案原子写入结论、原始备注、真实管理员和时间，同时解除对应待处理约束。

不要给提交指纹/终止记录、成功回执或已提交举报设置自动过期：原提交即使已结案、关联对象已消失，仍须能核实为成功；已明确终止的标识也不能重新创建举报。不要由商品/用户/会话删除逻辑级联删除举报与正式证据。

`submit` 的明确拒绝响应附带 `{ settled: true, rejected: true, submissionId }`，该确认只在拒绝栅栏的事务成功持久化后返回。所有同标识工作请求在最终事务检查栅栏，已成功记录优先回执。客户端不会单凭 4xx、鉴权失败或回执暂未查到就清除未知标识。

## 云存储

### 按官方能力建议的目录权限（待云端验证）

官方支持在同一个存储空间内通过路径条件区分权限；不必仅因前版规则保存报错就迁移存储。本配置是结合现有八个目录及用户提出的“所有人可读、仅创建者可写”模板整理的建议，尚未替换云端权限。

| 目录 | 客户端读取 | 客户端上传、覆盖及删除 |
| --- | --- | --- |
| `avatar/`、`product/`、`products/`、`system/` | 所有人 | 仅创建者 |
| `chat-staging/`、`report-staging/` | 仅创建者 | 仅创建者 |
| `chat-media/`、`report-evidence/` | 禁止直接读取 | 禁止 |
| 其他未列出的目录 | 禁止 | 禁止 |

完整建议 JSON 见 [storage-rules-by-directory.proposed.json](storage-rules-by-directory.proposed.json)。它使用带独立开头锚点及斜杠边界的正向路径匹配，不使用否定、正则分组或额外逻辑分组。普通正则或运算及锚点依据[官方云存储说明](https://docs.cloudbase.net/storage/security-rules)；每次 `.test()` 显式比较 `== true`，兼顾[规则语言说明](https://docs.cloudbase.net/rule/learn-rules)的要求。两篇官方页面对是否省略布尔比较的示例存在差异，不能据此把任何一版未经云端验证的表达式称为“已经可用”。

与用户最早提供的 `{ "read": true, "write": "auth != null" }` 相比，公开目录写权限收紧为创建者，未列出目录默认拒绝；新增业务目录需补充规则。此建议只面向当前小程序微信身份。云控制台和服务端 SDK 不受客户端规则限制；聊天图片由参与者鉴权后提供短期链接，举报证据由管理员鉴权后提供短期链接。数据库四个举报集合仍全部禁止客户端读写。

本地语法与权限逻辑验证不能替代实际保存与双账号验收。此前报错的具体原因未定，以下保留历史排查记录；不要将旧候选误当作已验证的部署配置。

### 实现边界及历史排查记录

| 前缀 | 内容 | 客户端权限 |
| --- | --- | --- |
| `report-staging/` | 服务端准备并绑定当前提交的随机上传目标 | 仅创建者读写 |
| `report-evidence/` | 服务端按真实图片字节校验后生成的独立随机副本 | 所有客户端禁止读写，包括举报人 |
| `chat-staging/`、`chat-media/` | 既有聊天临时文件与独立正式图片 | 保留原有隔离 |

服务端验证 `fileId` 的当前环境和完整路径与私有准备记录相符，再下载字节验证静态 JPEG/PNG/WebP、尺寸、CRC、实际可解码性与 10 MiB 上限。不可猜测的准备路径绑定和创建者权限共同约束临时上传归属；仅校验文件扩展名或前端传入的上传者不成立。正式副本不能被客户端替换或删除。

CloudBase 安全规则作用于客户端，服务端 SDK 仍可访问文件。规则是专用语言，不能把本地 JavaScript 表达式校验当成云端解析验证。官方“了解安全规则”的“特殊方法”明确要求 `.test(resource.path)` 必须显式与 `true` 或 `false` 比较；下面逐项比较，使用独立前缀表达式及 JSON 双反斜杠转义，不使用一元 `!` 或正则分组。[官方语法说明](https://docs.cloudbase.net/rule/learn-rules)、[官方云存储规则](https://docs.cloudbase.net/storage/security-rules)

**现场状态（2026-09-12）：用户反馈以下修订仍被微信云开发控制台拒绝，返回 `InvalidParameter, rule invalid`。该内容仅保留用于排查，不作为可部署配置。** 已核对报错引用的公开控制台脚本：调用的是 `ModifyStorageSafeRule`；“修改集合安全规则”是存储接口复用的标题，不能据此判断选错入口。编辑器将文本原样提交；具体失败原因尚未确认，需要核对实际编辑框文本并完成云端验证。

后续贴回文本显示 JSON 源字符串中的路径分隔符前有四个反斜杠，行首还出现 `&#x20;`。若编辑框原文确实如此，则存在双重转义及非法 JSON 字符；聊天传输也可能造成这种显示，因此尚不能据此确定云端失败的完整原因。为避免再次通过富文本复制，提供[纯 JSON 规则文件](storage-rules-report.json)：从文件编辑器全选复制，仅保留两个顶级字段；JSON 源字符串中的路径分隔符前应为两个反斜杠，解码后的规则表达式中为一个，不含 HTML 实体。本地 JSON 与权限逻辑检查通过，云端仍须重新保存并验证。

用户提供的现有存储规则为 `{ "read": true, "write": "auth != null" }`。以下待排查规则的目标是保留其他目录“所有人可读、已认证客户端可写”，将聊天和举报临时目录限制为创建者读写，正式目录禁止所有客户端读写。其他环境若原规则不同，须按其原条件合并。规则配置入口是**存储 → 权限 → 自定义安全规则 → 修改**，不用于数据库集合权限：

```json
{
  "read": "(/^chat-staging\\//.test(resource.path) == false && /^chat-media\\//.test(resource.path) == false && /^report-staging\\//.test(resource.path) == false && /^report-evidence\\//.test(resource.path) == false) || (auth != null && auth.openid != null && resource.openid == auth.openid && (/^chat-staging\\//.test(resource.path) == true || /^report-staging\\//.test(resource.path) == true))",
  "write": "auth != null && /^chat-media\\//.test(resource.path) == false && /^report-evidence\\//.test(resource.path) == false && ((/^chat-staging\\//.test(resource.path) == false && /^report-staging\\//.test(resource.path) == false) || (auth.openid != null && resource.openid == auth.openid))"
}
```

临时目录归属检查面向项目现有微信登录，其他目录保留原 `auth != null` 条件。此修订未在用户云端成功保存；在找到可接受的配置后，仍须等待 1–3 分钟生效并以测试账号验证。不能通过改成公开读写来绕过配置错误。不要将 COS 桶或 CDN 另设公开读取，使云存储安全规则失效。

后台 `getReportEvidence` 经启用的超级管理员鉴权并核实附件属于该举报后签发短期链接。前端只在当前详情内存中使用，不写入持久缓存或日志；短期链接在有效期内具有访问能力，不应外传。关闭原用户、商品或会话不影响管理员读取已保存的证据。

图片上传或服务端转存中断可能遗留未引用文件。临时文件可以制定延迟清理策略，但不能删除仍在提交/重试窗口中的文件。正式目录不能按时间整批删除：须先核对 `reports` 引用，并排除仍在运行或结果未知的请求。数据库提交结果未知时不盲删副本，避免删除实际已成功的举报证据。本次不创建后台清理任务。

## 云端与真机验收

使用测试账号 A、B、无关用户 C，启用的超级管理员，以及禁用/非超级管理员测试身份。避免修改生产用户数据。

- A、B 在同一商品的空会话均可举报对方；下架、售出和对方禁用仍可举报。会话、商品或对方真实删除以及本人非参与者时，拒绝新的举报。
- 一次选择多图后再次选择，总数不超过 9；验证真实静态 JPEG、PNG、WebP、伪装扩展名、GIF/APNG/动态 WebP、超 10 MiB、缺失本地文件、取消及权限拒绝。用接近 9×10 MiB 的真实图片确认执行超时与内存足够。
- 双客户端同时用不同提交标识提交同一账号、同一会话，只产生一份待处理记录；买卖双方各自举报互不阻塞。结案后允许新提交，旧提交重试仍回执为原成功。
- 在服务端成功写入后模拟客户端断网，离开重进、删除关联对象，再恢复网络；原成功回执仍可恢复，不能误建第二份举报。
- 用提交人、对方、无关账号尝试直接查四个集合、使用正式 `fileId` 下载/取链接/覆盖/删除，全部拒绝；用不同账号访问临时文件同样拒绝。通过 `chatService.getImage` 或公开商品 API 不能读取举报证据。
- 后台默认待处理，准备超过 20 条和同毫秒提交数据，检查稳定排序、全部/状态筛选、页码、详情返回刷新、处理后空页回退。记录消失后显示保留快照并可读取正式截图。
- 两个管理员同时提交相反结论，只保留一个结案结果；模拟处理响应丢失后刷新核实。备注边界为 1/200/201 Unicode 码点，含空白及换行；已结案不可改判。
- 提交/查看过程中退出账号或切换页面，迟到响应不能重新展示资料、清掉新草稿或错误返回；后台恶意 HTML 文本按原文显示。
- iOS 和 Android 微信检查三等分工具栏、头像和时间、原聊天草稿、表单键盘与换行、相册/拍照/预览、返回恢复，以及成功提示 2 秒后返回原会话。
- 举报和结案不生成聊天消息、未读数、通知；结案不自动禁用账号或下架商品。助手能说明真实举报入口，不承诺拉黑、在线客服、进度查询或自动处罚。

本地测试使用内存数据库和原生 API 替身，不能替代真实云环境的事务冲突、索引、存储规则及 iOS/Android 验收。
