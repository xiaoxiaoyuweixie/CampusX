### 2.3 新增数据和接口契约

本地实现已采用独立 `reportService` 云函数、小程序 `pages/report/index` 页面、举报集合 `reports`，后台继续通过 `adminService` 提供下表 action。另有提交指纹、单待处理互斥及附件准备三个辅助集合，见实施记录与部署说明。当前小程序不接入旧设计稿的 REST `/api/v1/reports`。

| 数据项 | 含义与要求 |
| --- | --- |
| 举报标识、提交标识 | 举报标识由服务端确定；客户端为一次逻辑提交生成稳定标识，原样重试不变。同一提交标识不能对应两份不同内容 |
| 举报人 / 被举报人 / 会话 / 商品标识 | 服务端从登录身份和会话确定；不得把“卖家”固定当作被举报人，买卖双方都可举报对方 |
| 举报原因 | 第 4.2 节七个固定值之一；建议内部原因码与文案映射，不接收任意自定义原因代替枚举 |
| 详细信息 | 原始有效文本，校验按 REQ-REPORT-FORM-002；不自动拼接聊天记录或联系方式 |
| 截图 | 有序的 0—9 个已校验、独立保存的证据引用及必要文件元信息；数据库不把临时预览 URL 当永久证据 |
| 提交快照 | 双方用户 ID、昵称/账号标识，商品 ID/标题，会话 ID 及双方与商品的关系；仅取核查所需信息，不复制密码、token、完整联系方式或整份用户对象。关联聊天仍走现有读取，不承诺全量历史聊天存档 |
| 状态 | 新举报默认“待处理”；规划新增枚举建议为 `pending` / `substantiated` / `unsubstantiated`，分别表示待处理/举报成立/举报不成立，不复用用户禁用或商品状态 |
| 提交时间 | 服务端实际成功创建时间，重试不覆盖；作为后台列表排序依据 |
| 处理信息 | 待处理时为空；结案时原子写入结论、备注、真实管理员 ID/显示名和服务端处理时间，按 REQ-REPORT-HANDLE-001 锁定 |

所有响应沿用 `{ code, message, data }`。小程序调用统一经过 API adapter；管理端仍使用 POST `{ action, data }` 并携带既有管理员 token。不得让任何客户端直接读写举报集合。

实现补充：提交发生并发重试时，普通 4xx 不等于原提交已终止。`submit` 仅在服务端通过事务阻止同标识材料继续写入后，于失败 `data` 返回 `{ settled: true, rejected: true, submissionId }`；客户端核对当前标识后才允许修正并创建新提交。若原举报实际已成功，服务端优先返回原成功回执。该技术约定落实后文“明确失败/未知/成功”的业务区别，不新增用户端处理进度查询。

| 调用责任 | 实际新增入口 | 成功及失败语义 |
| --- | --- | --- |
| 举报页初始化 | `reportService.getContext` | 接收 `sessionId`，校验本人及新举报所需对象，返回必要上下文/可提交状态；不能暴露其他人的举报或联系方式。最终新提交仍须重新校验。当前对象失效不能阻断同账号原提交的回执核实，初始化恢复顺序见第 4.1 节 |
| 准备截图 | `reportService.prepareEvidence` | 为当前账号、本次提交和附件签发受约束的临时上传目标；小程序通过 `wx.cloud.uploadFile` 上传文件，不操作数据库 |
| 提交举报 | `reportService.submit` | 接收会话、稳定提交标识、原因、详细信息和有序附件；服务端完成校验及原子写入后返回本次成功确认，不返回完整举报详情 |
| 核实响应丢失 | `reportService.getSubmissionResult`；`submit` 同时提供幂等回执 | 仅核实当前账号的指定提交是否已成功，返回最小成功标识；不能借此枚举其他举报或提供用户端处理进度功能。暂未查到不能直接宣称绝无正在执行的写入 |
| 后台列表与详情 | `adminService.listReports` / `getReportDetail` | 超级管理员可查询；列表沿用 `page/pageSize/total/list`，详情包含核查与处理需要的数据 |
| 后台截图 | `adminService.getReportEvidence` | 先验证管理员与举报/附件归属，再提供短期读取能力；不能依赖原会话或商品仍存在，不返回公开永久资源地址 |
| 后台处理 | `adminService.processReport` | 只允许待处理记录结案；处理人来自服务端鉴权。成功返回已持久化结果；冲突返回“已处理”及刷新指引，不能覆盖原结论 |

服务端拒绝、结果未知和已成功是三种不同情况；详细交互分别按 REQ-REPORT-SUBMIT-001、REQ-REPORT-SUBMIT-002、REQ-REPORT-HANDLE-002 执行。

## 7. 后台举报处理与留痕

### 7.1 处理流程

[图片占位：请放置「后台举报处理区 / 已处理详情」实现截图，用于说明结论、必填备注、提交状态及只读处理记录。]

1. 超级管理员阅读举报详情与证据，对待处理举报选择“举报成立”或“举报不成立”，填写处理备注。
2. 点击“提交处理”，服务端重新校验管理员与当前举报状态。
3. 成功时同时保存结论、备注、处理人和处理时间，提示“处理成功”，详情显示只读处理记录；后续列表按当前筛选反映最新状态。
4. 判为成立后，如需要禁用账号或下架商品，由管理员通过既有管理入口另行操作；不会因结案接口自动执行处罚。

| REQ-REPORT-HANDLE-002 | 并发处理、重复点击、明确失败或响应丢失 | 服务端至多接受一次从待处理到终态的转换，后续请求不得覆盖。明确失败保留填写内容，不伪称成功；响应未知时重新读取权威记录。已处理则展示已保存结论，必要时提示“该举报已处理，请刷新查看”，不能因重试覆盖备注或处理人 | 用户 C；原子性与终态要求 |
| REQ-REPORT-HANDLE-003 | 判定成立、判定不成立或另行处罚 | 判定仅改变举报状态；不自动改变账号、商品、聊天权限，不发送通知。原管理能力的开关操作独立执行，其成败不能回滚或重写已完成结案。不新增处罚期限或禁止卖家重新上架的机制，也不把“成立”展示成“已禁用/已下架” | 用户第 2 项、B、C；已确认既有入口复用 |

### 7.2 状态与操作

| 来源状态 | 触发 | 目标状态 | 持久化及禁止行为 |
| --- | --- | --- | --- |
