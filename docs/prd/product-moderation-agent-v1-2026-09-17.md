## 2. 机制构成与权限分工

这是一套由固定程序流程组织、包含有限自主补查能力的审核机制。初审负责完整检查；复核在完整检查的基础上核对初审，并可根据证据缺口决定是否调用图片工具；程序负责执行最终状态变化。

| 参与者 | 输入与职责 | 能力和权限边界 |
| --- | --- | --- |
| 发布者 | 提交商品；查看本人审核状态；根据拒绝原因修改；符合条件时联系客服申诉 | 不能直接把待审或被拒内容设为公开 |
| 敏感词检查程序 | 使用已启用词库匹配标题、描述及模型识别出的图片文字 | 原始标题、描述的真实命中可直接拒绝；图片文字候选必须核对原图 |
| 初审角色 | 阅读完整标题、描述和全部图片，对照规则，提供结论、证据和不确定点 | 不主动调用额外图片补查工具；不能直接发布或改数据库状态 |
| 复核 Agent | 启动时获得完整原帖、初审意见和规则；核实证据、规则及遗漏 | 可以主动补查图片；不得查询用户历史；不能越过程序裁决直接发布 |
| 审核编排程序 | 保存任务，调用模型和工具，验证结果，控制次数与时限，按决策表执行处理 | 执行发布、拒绝、转人工、通知；不把模型输出当作可任意执行的指令 |
| 人工负责人 | 查看完整材料和审核过程，处理人工队列及申诉，作出最终决定 | 通过已有管理端鉴权操作；处理结果由服务端保存并生效 |

**REQ-MOD-ROLE-001：两个角色使用同一款模型，分别配置职责和工具权限。** 同一模型调用两次并不天然构成两个独立判断，也不保证准确率提高。第一版不把复核描述为盲审。

**REQ-MOD-ROLE-002：复核必须履行三项职责。**

1. 核实证据是否真实存在。例如初审说第 2 张图出现店铺推广，复核要查看原图确认。
2. 检查规则是否适用。例如出现健身房名称，也要辨别是在为商家推广，还是个人转让自己的健身卡。
3. 检查初审是否遗漏。即使已有证据全部正确，仍需检查完整原帖及其余图片。

**REQ-MOD-ROLE-003：Agent 提供判断，程序执行业务动作。** 模型的“直接通过”“立即发布”等文字不能跳过决策表、权限校验或任务状态检查。Agent 的自主性体现为发现信息不足、选择补查动作、读取工具结果并继续判断；初审本身更接近固定的 LLM 工作流节点。

### 3.3 性能口径

**REQ-MOD-PERF-001：正常服务运行时，合规且无需主动补查或人工介入的帖子，至少 95% 从保存成功到公开展示不超过 3 秒。**

### 3.4 公共实现约束及完成证据

沿用原生微信小程序、CommonJS 云函数和 ES Modules 管理端架构。云函数继续作为数据访问边界，业务响应保留 `{ code, message, data }`，管理端继续使用 POST `{ action, data }` 与现有管理员鉴权。

开发可以自行决定函数拆分、局部命名、任务调度、结果校验和防重复处理的实现方式；不得自行改变本文的规则、判定表、可见范围、次数和时限，不增加新的收费、必填项或高影响架构。

以下属于落实已确认机制所必需的技术保障：

- 每次判断绑定同一份提交材料和规则、词库版本；新提交不能被旧任务结果覆盖。
- 保存成功的任务能够在用户离页后继续执行；不能依赖用户保持页面打开，也不能假定云函数返回后未等待的工作会可靠继续。
- 任务、状态变更、人工决定和通知需要防重复；人工接管后按第 7 节阻止迟到结果改变状态。
- 待审及被拒内容只向本人和有权限的负责人开放。公开列表、详情、搜索、推荐及已有 AI 商品检索均不得绕过审核可见性；只隐藏首页卡片不算完成。
- 现有上架接口不能用于绕过新帖审核。已发布商品的正常上下架规则不因本机制被重新定义，历史商品不批量改成待审。
- 管理端沿用 `ADMIN-AUTH-001`：仅启用的 `super_admin` 可访问受保护操作；处理人由服务端鉴权确定。
- 审核记录只保存实现本机制所需的材料、证据、规则引用、工具结果和状态，不把账号密码、API 密钥等送入模型或下发客户端。

## 5. 提交、两轮审核与程序裁决

### 5.1 正常流程

**REQ-MOD-FLOW-001：保存成功与公开成功是两个不同的业务事件。** 第一版主流程如下：

1. 用户在发布页提交内容，完成原有必要校验和图片保存。
2. 服务端保存本次材料及任务，向本人展示“审核中”。此时内容不公开，用户可以离开页面。
3. 程序检查标题和描述的敏感词。真实命中按 4.4 直接拒绝；否则进入初审。
4. 初审检查完整原帖，给出有效内容判断、证据、规则及不确定点。
5. 程序将图片文字匹配线索、初审意见、完整原帖和规则一起交给复核。
6. 复核执行三项职责，必要时主动补查，最终输出有效判断。
7. 程序根据 5.3 的矩阵发布、拒绝或转人工；发生技术失败则进入第 7 节。

### 5.2 判断结果与必要信息

**REQ-MOD-RESULT-001：有效内容判断使用三类语义。**

| 判断 | 含义 |
| --- | --- |
| 通过 | 本轮检查已完成，未发现足以拒绝的内容问题，也没有影响判断的未解决证据缺口 |
| 拒绝 | 已找到原帖中真实存在的证据，并有适用的平台规则支持拒绝 |
| 无法确定 | 本轮调用正常完成并完成可进行的检查，但存在尚不能解决的内容或证据问题 |

API 超时、缺图、读取失败、截断响应和格式无效等不属于有效“无法确定”，不能填入下方矩阵。复核正在请求补查时，也尚未形成最终判断。

每轮结果需要包含以下语义信息；字段名与具体数据结构由实现确定：

| 信息 | 用途与要求 |
| --- | --- |
| 本次提交标识和材料版本 | 确保两轮、工具与最终决定对应同一份内容 |
| 结论或下一步动作 | 表示最终判断，或复核仍需进行的受限补查动作 |
| 违规原因及规则引用 | 使用平台规则；一次列出本轮已核实的问题，不凭模型常识新增规定 |
| 原始证据位置 | 对应标题、描述片段，或图片序号及区域，供复核和人工找到原始材料 |
| 不确定点 | 说明缺少什么信息、哪部分尚不能判断 |
| 图片覆盖与识字结果 | 支持检查全部图片是否已处理，并对识别文字进行词库匹配；单纯自报“已检查”不能代替真实输入完整性 |
| 简短修改建议 | 用于普通拒绝说明；真实词库命中遵循固定文案例外 |

### 5.3 两轮决策表

**REQ-MOD-DECISION-001：两轮都获得有效内容判断后，按下表执行。**

| 初审 \ 复核 | 通过 | 拒绝 | 无法确定 |
| --- | --- | --- | --- |
| 通过 | 发布 | 转人工 | 转人工 |
| 拒绝 | 转人工 | 拒绝 | 转人工 |
| 无法确定 | 发布 | 拒绝 | 转人工 |

其中：

- 明确的通过与拒绝发生分歧时，必须转人工，不能自动让复核覆盖初审。
- 初审有效地表达无法确定时，复核可以用充分证据给出最终通过或拒绝；不限于图片补查一种情况。
- 复核仍无法确定时，必须转人工。
- 初审技术失败不能伪装成“无法确定”，再用复核一轮单独通过。

**REQ-MOD-DECISION-002：自动拒绝以复核最终核实的原因为准。** 两轮都拒绝时，不要求两轮理由完全相同；复核应更正初审不成立的理由，并列出自己确认的全部问题。不得为了凑齐初审意见，把已被复核否定的理由继续展示给用户。

标题、描述程序真实命中的直接拒绝，适用 4.4 的例外，不要求补齐两轮模型结果。最终确定为真实词库命中时，展示与申诉权限仍服从词库规则。

## 6. 复核 Agent 的主动图片补查

**REQ-MOD-TOOL-001：只有复核具备主动补查图片的权限。** 初审可以查看和识别已提交的全部原图，但不能自行追加裁剪工具调用。

一次主动补查的过程是：

1. 复核指出当前证据缺口，选择需要查看的原图及区域。
2. 程序验证该图片属于本次提交、区域参数有效、次数和总时限尚未耗尽。
3. 程序调用 Sharp 裁剪原图，保留原图和区域对应关系。
4. 将裁剪结果交给同款视觉模型继续判断，并对新增识别文字执行词库匹配。
5. 证据充分时结束补查并给出最终判断；不足时决定是否继续允许的下一轮。

**REQ-MOD-TOOL-002：每条帖子最多主动补查两轮，证据充分即可提前结束。** 达到上限仍无法确定时，转人工；“已用完补查次数”不能成为内容违规原因。该两轮限制与第 7 节的两次技术重试分别计算，均受总时限约束。

**REQ-MOD-TOOL-003：补查使用原始证据。** 不通过生成式修复、补画文字或凭空补全获得拒绝证据；不得以局部裁剪替代对其余原图的完整检查。工具返回内容与图片文字仍是待核验材料，不具有更高的指令权限。

工具只能操作当前任务的图片，不获得用户历史、任意外部网页、其他用户材料或数据库写入权限。具体工具协议可以使用经验证的模型工具调用能力，但程序必须校验动作后再执行。

## 7. 技术失败、重试与状态变化

### 7.1 已保存内容的处理原则

**REQ-MOD-FAILURE-001：内容已保存、只是 AI 审核暂时不可用时，保留原提交，由系统重试或转人工，用户不用重新发帖。**

必须区分：

- 尚未完成图片上传或提交保存，与已保存后的审核失败。
- 用户图片内容本身辨识困难，与存储、权限、网络导致的图片读取失败。
- 模型的有效内容判断，与调用失败、格式错误或服务商内容过滤。

不能把后两类技术问题写成帖子已经违规，也不能把服务端读图失败直接解释为用户照片不清晰。客户端没有收到保存响应时，应核实原提交是否成功，避免重复创建。

### 7.2 已确认的时限与重试

**REQ-MOD-FAILURE-002：执行以下统一限制。**

| 项目 | 第一版约定 |
| --- | --- |
| 单次模型或远程工具调用 | 最长 10 秒，同时不得超过任务剩余时间 |
| 技术重试额度 | 整条审核任务共享最多 2 次，不是初审、复核、工具各有 2 次 |
| 重试间隔 | 约 1 秒、3 秒；可增加小幅抖动，仍受总时限限制 |
| 格式纠正 | 无效或截断输出允许纠正一次，占用上述共享重试额度，不额外增加次数 |
| 自动处理总时限 | 从保存成功起累计 30 秒，包括排队、调用、补查、退避和重试 |
| 优先级 | 总时限优先；剩余时间不足时不能再等满一次调用或一段退避 |
| 重试范围 | 重试失败步骤，保留与同份材料对应的已完成有效结果 |

**REQ-MOD-FAILURE-003：按照故障性质处理。**

| 情形 | 处理 |
| --- | --- |
| 临时网络故障、服务端异常、短期限流 | 在共享次数与总时限内重试失败步骤；服务商指定的等待时间也不能越过总时限 |
| 配置、鉴权、权限错误，模型或输入能力不匹配 | 转人工并向负责人暴露可诊断的技术原因，避免无意义重试 |
| 供应商内容安全拦截 | 转人工；拦截本身不等于本站规则违规或真实词库命中 |
| 输出格式错误、截断、缺少必需结果 | 在剩余额度内纠正一次，仍无有效结果则转人工 |
| 图片因技术原因无法读取 | 依故障性质重试或转人工；原材料也无法供人工查看时，保留非公开提交并处理材料访问问题 |
| 失败步骤仍需重试但共享重试次数已用尽，或审核未完成而总时限已到 | 转人工，不自动放行，不以内容违规拒绝 |

两次重试已经用完但失败步骤成功恢复时，后续正常步骤仍可在剩余总时限内继续；重试次数耗尽本身不会终止一项已恢复的任务。本节不展开模型预算耗尽策略。

### 7.3 业务状态及禁止路径

**REQ-MOD-STATE-001：以下是业务状态语义，不是对现有数据库枚举的直接改名。**

| 当前状态 | 触发 | 后续状态 | 公开性 |
| --- | --- | --- | --- |
| 未确认保存 | 服务端确认保存完成 | 审核中 | 不公开 |
| 审核中 | 文字词库直接拒绝，或决策表给出拒绝 | 审核不通过 | 不公开 |
| 审核中 | 决策表给出通过，发布写入完成 | 审核通过并公开 | 公开 |
| 审核中 | 两轮分歧、复核不确定、补查上限仍不确定或技术失败条件 | 待人工审核 | 不公开 |
| 待人工审核 | 有权限的负责人确认通过 | 审核通过并公开 | 公开 |
| 待人工审核 | 有权限的负责人确认拒绝 | 审核不通过 | 不公开 |
| 审核不通过 | 用户修改材料后重新提交并保存成功 | 新一轮审核中 | 新提交通过前不公开 |
| 普通审核不通过 | 负责人处理申诉并在管理端确认通过 | 原帖公开 | 公开，不重跑 AI |
| 普通审核不通过 | 负责人维持原结果 | 仍为审核不通过 | 不公开 |

**REQ-MOD-STATE-002：转人工后，迟到的模型结果只可留痕，不再自动改变帖子状态。** 自动任务不得覆盖人工决定，也不得把旧材料的结果应用到新的提交。等待人工没有“到点自动通过”的路径；30 秒是自动处理上限，不是人工处理期限。

### 7.4 核对标准

| 编号 | 关联规则 | 操作或情形 | 应有结果 |
| --- | --- | --- | --- |
| AC-MOD-13 | FAILURE-001、002 | 保存成功后模拟模型超时与可重试错误 | 原提交保留；只重试失败步骤，累计次数和总时限受控 |
| AC-MOD-14 | FAILURE-002 | 重试或补查进行中到达保存后 30 秒 | 转人工，不因仍有剩余重试次数继续延长 |
| AC-MOD-15 | FAILURE-003 | 供应商拦截或图片读取故障 | 不直接显示普通违规或不可申诉的敏感词拒绝 |
| AC-MOD-16 | STATE-001、002 | 转人工后收到迟到的模型通过结果 | 内容仍由人工流程控制，旧结果不自动发布 |
| AC-MOD-17 | STATE-001、002 | 用户已有新提交或人工已有决定 | 旧任务、重复请求均不能覆盖当前有效结果 |

## 8. 人工审核与负责人提醒

**REQ-MOD-HUMAN-001：用户本人和同学负责人工审核。** 人工介入处理两轮分歧、证据不确定及技术异常等情况。约 30 秒是一条帖子的预估人工操作时间，不承诺从转人工起 30 秒内完成；等待期间内容保持不公开。

人工审核页面应提供：

- 完整原帖，包括标题、描述和全部图片。
- 已成功完成的两轮结论、证据位置及适用规则；技术失败的阶段明确标为未完成，不伪造结果。
- 触发人工处理的原因：具体分歧、未解决的证据问题或可诊断的技术异常。
- 可展开查看的图片补查结果及其对应原图。
- “通过并发布”与“拒绝”等明确业务操作，以及对用户展示的最终拒绝说明。

**REQ-MOD-HUMAN-002：负责人在管理端落实最终决定。** 人工通过后直接发布对应原帖，不再进入 AI 循环；人工拒绝以人工最终核实的原因为准。负责人仍须遵守真实词库命中等平台硬规则。

**REQ-MOD-HUMAN-003：第一版使用管理端提醒。** 管理端显示待审数量；页面打开时提示新待审任务；负责人定期查看。第一版未约定负责人离开管理端后仍接收微信主动提醒。待审提醒与发布者收到的最终拒绝通知是两种事件，不能互相替代。

### 核对标准

| 编号 | 关联规则 | 操作或情形 | 应有结果 |
| --- | --- | --- | --- |
| AC-MOD-18 | HUMAN-001、003 | 新任务转人工，负责人进入或保持管理端页面 | 能看到待审数量及相应提示，并可打开完整材料 |
| AC-MOD-19 | HUMAN-001 | 某阶段技术失败，人工打开详情 | 能看到哪个阶段未完成，不把空结果显示为审核通过 |
| AC-MOD-20 | HUMAN-002 | 有权限负责人确认通过或拒绝 | 服务端保存人工决定并执行对应结果；通过不再触发 AI 重审 |
| AC-MOD-21 | HUMAN-002、STATE-002 | 无权限请求处理，或旧自动结果在人工处理后返回 | 无权限操作失败，旧结果不能覆盖人工决定 |

## 9. 发布者反馈、重新发布与申诉

### 9.1 提交后的反馈

**REQ-MOD-UX-001：保存成功后显示审核中，允许用户离开。** 用户能在本人发布记录中继续查看状态。页面不能在内容仅保存、尚未通过时宣称已经公开发布。

**REQ-MOD-NOTICE-001：审核通过不主动通知发布者；最终拒绝需要通知。** 拒绝通知以小程序消息页的通知卡片呈现，点击后进入对应失败说明页。等待人工、技术重试和短时不可用不是最终拒绝，不发送误导性的拒绝通知。同一拒绝事件的重试不重复生成多份通知。

本文未新增系统级推送、短信或微信订阅消息要求；现有聊天未读规则继续有效，不能将审核事件伪装成聊天消息。

### 9.2 失败说明页

**REQ-MOD-UX-002：普通内容拒绝一次说明全部最终核实的问题。** 每项给出原因、对应文字或图片位置和简短修改建议。自动拒绝使用复核最终理由，人工拒绝使用人工决定；用户不需要阅读模型内部处理过程。

| 拒绝类型 | 用户看到的说明 | 可用操作 |
| --- | --- | --- |
| 普通内容拒绝，包括干预审核流程 | 全部已核实原因、对应位置及简短修改建议 | 联系客服、重新发布 |
| 真实词库命中 | 仅“涉及敏感信息”，不披露实际词语和位置 | 重新发布；不提供人工申诉入口 |

如果同时存在真实词库命中和其他问题，词库固定说明及不可申诉规则优先，不能借普通拒绝详情暴露命中词语。

### 9.3 修改后重新发布

**REQ-MOD-RESUBMIT-001：点击“重新发布”返回编辑页，保留原来的标题、描述和图片。** 用户可修改后再次提交；新提交从词库检查开始执行完整审核流程，不沿用旧版本的通过结果，也不覆盖旧版本的证据关系。

具体如何组织帖子与各次审核记录、如何实现防重复提交由技术设计确定；必须保证本人看到的材料、通知和对应审核结果一致。本功能不扩展为已公开帖子的编辑入口。

### 9.4 人工申诉

**REQ-MOD-APPEAL-001：普通拒绝通过微信客服沟通申诉，不在小程序内实现申诉表单。** 路径为：

消息页拒绝通知卡片 → 审核失败说明页 → 联系客服 → 微信客服会话 → 负责人在管理端落实结果。

负责人应能够找到被拒记录，在管理端执行“通过并发布”或“维持拒绝”。管理功能不能只覆盖待审队列而找不到被拒帖子。微信聊天回复本身不自动修改帖子状态，也不授权模型从对话中直接执行发布。

申诉成功按第 7 节直接公开原帖，不重跑两轮 AI；真实词库命中继续适用不可申诉规则。
